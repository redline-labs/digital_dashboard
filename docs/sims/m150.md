# m150_sim

## Overview

`m150_sim` runs an M1 application on an emulated MoTeC M150 (an M1 "ecu120"):
an MPC5554 on an e200 core ([e200](../libs/e200.html),
[mpc55xx](../libs/mpc55xx.html)), the board's memory, and its three CAN buses.
`m150_sim serve` puts those buses on zenoh exactly where `can_bridge` would put
a real unit's, so the nodes and tools downstream see an M150 on the bus.

It needs an image of the ECU's internal flash: a kernel and the M1 application
it runs. MoTeC's kernel is encrypted and does not run here. An MVP kernel with
the system-call ABI an M1 application expects stands in for it, built outside
the tree with an application that M1 Build compiled. Nothing built for the
target is in the repository.

## Running it

```bash
export M150_IMAGE=/path/to/m150_mvp.bin
build/sims/m150/m150_sim serve
```

The kernel boots, loads the application and starts it; its console goes to the
log. The test application sends `0x123` on `vehicle/can0/rx` every 10 ms.

| Verb | What it does |
|---|---|
| `serve` | Runs the M150 in real time with its CAN on the bus, and answers agent calls with `--mcp`. |
| `run [IMAGE]` | Runs an image for `--seconds` (default 2) as fast as the emulator can. The console goes to stderr and every frame on the three buses to stdout in candump format. `--candump-in FILE` sends a log's frames onto the buses, the first at 0.3 s. |

`serve`'s options:

| Option | Meaning |
|---|---|
| `-c FILE` | The serve configuration, below. Optional. |
| `--image FILE` | The flash image. Default `$M150_IMAGE`. |
| `--engine interp\|block\|jit` | The CPU engine. Default `jit`. |
| `--stepped` | Simulated time moves only when an agent calls `run`, not with the wall clock. |
| `--mcp[=SOCKET]` | The agent control socket; prints `AGENT_READY` when serving. |

The global `--connect` and `--mode` options choose the zenoh session, as for
every tool built on `cli::Program`.

## Configuration

Every key is optional; an unknown key is an error. The M150 has three CAN ports.
CAN1 is on `can0` unless the file says otherwise; CAN2 and CAN3 are off until
they are named.

```yaml
can:
  CAN1: {name: can0}         # rx_key, tx_key and record_trc as for pdm32_sim
  CAN2: {name: can1}
  CAN3: off
image: /path/to/m150_mvp.bin
engine: jit
stepped: false
```

Which FlexCAN controller drives which connector pair is not known: A, B and C
are taken as CAN1, CAN2 and CAN3.

## Topics

| Key | Schema | Direction |
|---|---|---|
| `vehicle/can0/rx` (and each named port's) | `CanFrame` | The M150's frames. `channel` is the port's configured name; `timestampUs` is simulated time since power-on. |
| `vehicle/can0/tx` (and each named port's) | `CanFrame` | Frames for the M150. Classic CAN only. |
| `nodes/m150_sim/health` | `NodeHealth` | As every node publishes. |

## The image

A raw image of the 2 MB internal flash, as the part holds it:

- the kernel from address 0, its reset configuration word first;
- the application's text in place at its link address, 0x100000;
- its initialised data, which the kernel copies to external RAM.

The research tree's `emu/m150_mvp` builds one: its kernel with an application
built by M1 Build (`build.sh APP.elf`). The README there covers the kernel's
system calls and what it does not do yet.

To run the image-backed tests (`m150_test_boot`, `m150_test_serve`), configure
with `-DM150_IMAGE=/path/to/m150_mvp.bin`. Without it they skip.

## What is real and what is not

The application is a real M1 application, compiled by M1 Build against MoTeC's
libecu. The kernel is not MoTeC's: it implements the system calls, threads,
signals and CAN devices the application uses, and returns zero for the hardware
functions (`iofn2`). It has no analog or digital I/O, injection or ignition.

The emulated part covers what that needs:
- the boot ROM's reset work (the ROM itself is not in the tree);
- the e200 core with its MMU and the SPE's single precision;
- the interrupt controller;
- FlexCAN A–C, at the programmed bit rate;
- eSCI A as the console.

The rest of the MPC5554's modules, and the FPGA's window on the external bus,
are storage. The first write to each register is logged as a `model gap:`
warning, so a run says what it touched.

Some board details are assumptions:
- the part is taken to be an MPC5554;
- external RAM is taken to be 4 MB at 0x20000000;
- the FlexCAN interrupt sources come from the reference manual, unchecked against hardware.

The board's I/O (connectors, pins, driver devices, hardware functions) is
described in `sims/m150/board/topology`, but nothing drives it yet.

The M150's Ethernet (XCP on UDP 5555, mDNS, the CAN gateway) is not simulated.

## Driving it from an agent

`serve --mcp` answers agent calls on the
[agent control](../developing/agent-control.html) socket:

| Method | What it does |
|---|---|
| `status` | Time, pc, MSR, the engine and its counters, and each CAN controller's bit rate and frame counts. |
| `console` | `{lines=50}`: the console's last lines. |
| `run` | `{seconds}`: advance time (stepped mode only). |
| `app.info`, `app.logs` | As for every simulator. |

`m150_sim` is not yet one of the apps the MCP server launches; start it by hand
and connect to its socket.

## Troubleshooting

**It exits with "no image".** Pass `--image`, put `image:` in the config, or
set `M150_IMAGE`.

**"no reset configuration at the start of flash".** The file is not a flash
image: its first word must carry the boot identifier 0x5A.

**The console shows `[kernel] ... exception`.** The application touched
something the MVP kernel does not map or implement; the line gives the pc,
the faulting address and the ESR.
